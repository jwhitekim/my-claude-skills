# test-gap-finder

변경된 소스 파일마다 대응하는 테스트 파일이 있는지 기계적으로 확인하고, 없으면
Claude가 직접 테스트 코드를 작성한다. "테스트가 새 분기/엣지케이스를 실제로
커버하는가"는 의미 판단이라 스크립트가 하지 않는다 — 그건 diff와 기존 테스트를 읽고
Claude가 판단한다.

## 실행

```bash
bash ~/.claude/skills/test-gap-finder/scripts/find-gaps.sh          # staged 변경 기준 (기본)
bash ~/.claude/skills/test-gap-finder/scripts/find-gaps.sh last     # 마지막 커밋 기준
```

테스트 파일 자체(경로에 `test_`, `_test`, `.test.`, `.spec.`, `tests/`, `__tests__/`가 있는
파일)는 검사 대상에서 제외한다.

### 사소한 변경은 자동으로 거른다 (jev-eval)

테스트 파일이 없는 소스 파일마다 그 파일의 diff를 `jev-eval`에 보내 "테스트가 필요한
로직 변경인가?"를 0~1 확률로 받는다. 출력 줄은 세 가지다:

| 출력 | 의미 |
|---|---|
| `사소한 변경으로 판단해 제외 (테스트 필요 확률 0.04)` | 확률 0.5 미만 — 포맷팅·주석·이름 변경 등. 테스트를 요구하지 않는다 |
| `대응하는 테스트 파일 없음 (테스트 필요 확률 0.94)` | 로직 변경 — 테스트를 챙겨야 한다 |
| `대응하는 테스트 파일 없음 (jev 판정 실패 — 거르지 않음)` | 키 없음·크레딧 부족 등으로 판정 못 함. 안전하게 그대로 보고한다 |

제외된 파일도 이유와 함께 보여주므로, 판정이 이상해 보이면 Claude가 diff를 직접 보고
뒤집을 수 있다. diff는 jev 입력 한도 때문에 앞 20,000자까지만 보낸다.

## 판단/작성은 Claude가 한다

1. **jev 판정이 실패했거나 미심쩍은 경우** — 해당 파일 diff를 직접 읽고 로직 변경인지
   판단한다.
2. **테스트 파일이 없는 경우** — 해당 소스 파일을 읽고, 같은 프로젝트의 기존 테스트
   파일(다른 모듈 것이라도)을 하나 참고해서 테스트 프레임워크/스타일을 파악한 뒤,
   같은 컨벤션으로 새 테스트 파일을 작성한다. 정상 케이스 + 이번 diff가 추가한 분기/
   엣지케이스를 커버한다.
3. **테스트 파일은 있지만 이번 변경을 안 건드린 경우** — `find-gaps.sh`는 이 케이스를
   잡지 않는다(오탐이 많아서 제외함). Claude가 diff와 기존 테스트를 직접 비교해서,
   새로 생긴 분기가 비어 보이면 테스트 케이스를 추가한다.
4. **작성한 테스트는 실제로 돌려서 통과를 확인한다.** 통과 확인 없이 "테스트를
   추가했다"고 보고하지 않는다.

## change-impact와의 연계

`change-impact`가 diff에 소스 파일 변경이 있으면 `find-gaps.sh`를 대신 호출한다. 갭이
있으면 사용자에게 보여주고 테스트를 작성할지 확인받는다. 테스트 없이 진행하는 걸 막지는
않는다 — 판단은 사용자에게 맡긴다.

## 하지 않는 것

- **커밋을 막지 않는다.** 정보 제공 + 제안까지만 자동이고, 테스트 작성 여부와 커밋
  진행은 항상 사용자 확인을 거친다.
- **테스트 커버리지 퍼센트 계산 안 함.** "파일 단위로 테스트가 존재하는가"만 본다.
- **기존 테스트가 부실한지는 판단하지 않는다.** 테스트 파일이 존재하기만 하면
  "파일 없음" 갭에서는 제외된다.
