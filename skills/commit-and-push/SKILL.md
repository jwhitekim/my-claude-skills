# 커밋 & 푸시

커밋과 푸시는 되돌리는 비용이 다르다. 커밋은 로컬이라 거의 공짜로 되돌릴 수 있지만,
푸시는 원격에 올라가면 되돌리는 데 force push가 필요하다. 그래서 **커밋 전 검증은
자동으로, 푸시는 사람 확인을 조건으로** 한다.

## 0. 커밋 자동화 규칙 부트스트랩

프로젝트의 규칙 파일(`.claude/rules/`, `CLAUDE.md`, 또는 비표준 `.claude/RULES.md`)에
"커밋 자동화" 규칙이 아직 없으면, 다음 스크립트로 (마커 포함) 한 번만 추가한다. 이미
있으면 아무것도 하지 않는다(중복 삽입 방지 — 직접 grep해서 확인해도 되고, 그냥 실행해도
안전하다). `.claude/rules/`가 있으면 그 안에 `commit-automation.md`를 새로 만들고,
없으면 기존 단일 파일에 이어붙인다:

```bash
bash ~/.claude/skills/commit-and-push/scripts/install-auto-commit-rule.sh
```

이 규칙이 있는 프로젝트에서는 검증(1번)을 통과한 기능/버그 수정 작업을 사용자의 별도
요청 없이도 커밋(3번)까지 진행한다. **푸시(4번)는 이 자동화에 포함되지 않는다** — 원격에
영향을 주는 작업이라 항상 사람 확인을 받는다.

## 1. 프로젝트 툴체인 감지

파일 존재 여부만으로 판정 가능한 기계적 작업이라 스크립트로 뺐다:

```bash
bash ~/.claude/skills/commit-and-push/scripts/detect-verify-cmd.sh
```

프로젝트 루트에서 실행하면 실행 가능한 검증 명령을 한 줄씩 출력한다(예:
`npm run build`, `pytest -q`). 출력된 명령을 그대로 실행하고 결과를 확인한다.
**아무것도 출력되지 않으면** 이 스크립트가 아는 스택이 아니라는 뜻이다 — 프로젝트의
`README`/`Makefile` 등에서 직접 찾거나, 검증 수단이 정말 없으면 사람에게 알리고 검증
없이 커밋할지 확인받는다.

수정한 파일이 스크립트가 못 잡는 언어(`.js`/`.py` 개별 구문 검증 등)면 해당 언어의
구문 검증 명령을 추가로 직접 실행한다.

증거(명령 실행 결과 전체)를 보고에 포함한다. "통과했다"고 말로만 하지 않는다.
검증이 실패하면 커밋하지 않고 사람에게 무엇이 실패했는지 보고한다.

## 2. staged 파일 검토

민감 파일 패턴 감지는 기계적으로 가능해서 스크립트로 뺐다:

```bash
bash ~/.claude/skills/commit-and-push/scripts/check-staged.sh
```

staged 파일 목록과, 그 중 `.env`/`secrets/`/`*.pem`/`*.key`/`id_rsa` 패턴에 걸리는 항목을
따로 보여준다. **경고 항목이 나오면 그 파일은 어떤 경우에도 커밋 대상에서 제외한다.**

이 스크립트가 못 하는 것 — 여기서부터는 Claude가 직접 판단한다:
- **staged 목록이 이번 작업 범위와 의미상 맞는지.** 사이드 이펙트로 건드려진 파일이
  섞였는지는 diff 내용을 읽고 판단해야 한다 — 스크립트는 목록만 보여줄 뿐 "의도한
  범위인지"는 알 수 없다.
- 테스트 파일을 대량으로 수정/삭제하는 커밋이면, 커밋 전에 사람에게 승인을 받는다

## 3. 커밋 단위

한 커밋 = 한 논리적 변경. 작업을 여러 단계로 나눠 진행했다면, 단계마다 커밋한다.
한 번에 몰아서 큰 커밋 하나로 만들지 않는다.

**커밋 메시지 형식** — 영어, type prefix, 전체 메시지 100자 이내(넘으면 본문부터 생략):

```
{type}: {what}
```

| Type | 사용 시점 |
| --- | --- |
| `feat` | 새 기능 | `fix` | 버그 수정 | `docs` | 문서 |
| `style` | 포매팅(기능 변경 없음) | `refactor` | 리팩토링 | `test` | 테스트 코드 |
| `build` | 빌드 설정 | `ci` | CI 설정 | `perf` | 성능 개선 |
| `chore` | 패키지 매니저/잡무 | `rename` | 이름만 변경 | `remove` | 삭제만 |

예: `feat: add soft delete for tasks`

**실제 커밋 실행**은 `git add` + `git commit`을 따로 치지 않고 아래 스크립트로 한다 —
민감 파일 패턴이 하나라도 섞여 있으면 2번의 경고와 달리 **커밋 자체를 거부**하는
하드 가드레일이다:

```bash
bash ~/.claude/skills/commit-and-push/scripts/safe-commit.sh "{type}: {what}" <file1> [file2 ...]
```

## 4. 푸시 — 검증 게이트 + 사람 확인 게이트

프로젝트가 브랜치 전략을 명시하지 않았다면(`main` 하나만 쓰는 게 일반적) 새 브랜치를
만들지 않는다. 이미 작업 중인 브랜치가 있으면 그 브랜치에 푸시한다.

**4-1. 재검증** — 1번의 검증 명령을 이전 커밋들과 합쳐진 상태에서 한 번 더 실행한다.
실패하면 푸시하지 않고 사람에게 보고한다(로컬 커밋은 되돌릴 필요 없음).

**4-2. 사람 확인** — 재검증을 통과했어도 곧바로 푸시하지 않는다. 푸시할 커밋 목록(해시 +
메시지)과 재검증 결과를 보여주고, 사람이 "푸시해" 또는 그에 준하는 명확한 승인을 준 뒤에만
`git push` 한다. 커밋 메시지가 실제 변경과 맞는지 확인하는 게 이 게이트의 핵심이다 —
이 일치 여부는 의미 판단이라 스크립트로 대체할 수 없다.

이 확인 게이트는 판단 정확도의 문제가 아니라 **원격 저장소에 영향을 주는 되돌리기 어려운
작업이라는 성격 자체** 때문에 있다. 아무리 정교한 스크립트/판정 로직을 붙여도 이 단계는
생략하지 않는다.

승인을 받은 뒤 실제 push는 아래 스크립트로 한다. fast-forward만 허용하고, 원격이
로컬에 없는 커밋을 갖고 있으면(뒤처짐/분기됨) 무조건 거부한다 — **force push 옵션
자체를 받지 않으므로 이 스크립트로는 구조적으로 force push가 불가능하다.** force push가
정말 필요한 상황이면 이 스킬의 범위 밖이니 사람이 직접 위험을 인지하고 실행해야 한다.

```bash
bash ~/.claude/skills/commit-and-push/scripts/safe-push.sh [remote] [branch]
```

거부되면(exit 1) 원격에 로컬이 모르는 커밋이 있다는 뜻이다 — pull/rebase로 반영한 뒤
다시 검증(4-1)부터 거친다.

**4-3. 배포 확인(있으면)** — 프로젝트에 `.github/workflows/`가 있고 push가 그 워크플로를
트리거하는 걸로 보이면, 푸시 후 `deploy-status` 스킬로 넘겨 실제 배포 성공 여부까지
확인한다. 워크플로가 없으면 이 단계는 건너뛴다.

## 5. 완료 보고

커밋 목록(해시 + 메시지), 마지막 검증 결과, 푸시된 브랜치를 보고한다. 4-3을 실행했으면
배포 상태도 함께 보고한다.

## 하지 않는 것

- `git push --force` (사용자가 명시적으로 요청하고 위험을 인지한 경우가 아니면 하지 않음)
- 사람 확인 없이 푸시
- 브랜치 전략이 없는 프로젝트에서 임의로 새 브랜치 생성
- 커밋 히스토리 재작성(`rebase -i` 등 — 메시지만 고치는 `commit --amend`는 예외)
- 검증 실패 상태에서의 푸시
- `.env`, `secrets/` 등 민감 파일 커밋
