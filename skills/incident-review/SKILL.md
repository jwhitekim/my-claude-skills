# incident-review

장애 회고 문서를 쓰는 데 필요한 재료를 모으고, 정해진 양식으로 정리한다. 누구 탓인지가
아니라 **무엇이 문제였고 어떻게 막을지**에 초점을 둔다(blameless).

## 1. 사용자에게 받을 것

- **장애 시각** (대략이라도) — `YYYY-MM-DD HH:MM`
- **무슨 일이 있었는지** 한두 줄 (증상, 누가/어떻게 알아챘는지)
- **서버 런타임 로그**가 있으면 붙여넣어 달라고 한다 — Vercel/서버 로그는 이 스킬이 자동으로
  가져오지 않는다.

시각을 모르면 "마지막으로 정상이던 때"와 "이상을 발견한 때"를 묻고 그 사이를 범위로 잡는다.

## 2. 재료 모으기

```bash
bash ~/.claude/skills/incident-review/scripts/collect.sh "<장애 시각>" [앞뒤 범위 시간, 기본 24]
```

- 범위 안의 **커밋** 목록 (모든 브랜치)
- 범위 안의 **GitHub Actions 실행** 기록과 성공/실패
- 실패한 실행의 **로그 끝부분** (최대 3개, 정리 단계 잡음은 잘라냄)

`gh`가 없거나 로그인이 안 됐거나 GitHub 원격이 없으면 Actions 부분만 건너뛴다. 실패 로그가
더 필요하면 `gh run view <run id> --log-failed`로 직접 더 본다.

## 3. 문서 쓰기

`docs/incidents/YYYY-MM-DD-<짧은-영문-제목>.md`로 저장한다(날짜는 장애 발생일). 양식:

```markdown
# <한 줄 제목>

- 발생: YYYY-MM-DD HH:MM
- 해소: YYYY-MM-DD HH:MM (지속 시간)
- 심각도: 높음 / 중간 / 낮음

## 요약
무슨 일이 있었고, 원인이 뭐였고, 어떻게 해결했는지 3문장 이내.

## 영향
누가/무엇이 어떤 영향을 받았는지. 모르면 "확인 안 됨"으로 적는다.

## 타임라인
- HH:MM 커밋 abc1234 "..." 푸시
- HH:MM 배포(run 123) 실패 — <로그 핵심 한 줄>
- HH:MM 이상 발견 (어떻게)
- HH:MM 수정 커밋 def5678 → 배포 성공

## 원인 분석
직접 원인 → 그게 왜 생겼는지 → 왜 미리 못 잡았는지 순서로 파고든다.
로그/커밋 근거를 인용한다. 추측이면 추측이라고 적는다.

## 잘된 점 / 아쉬운 점
- 잘된 점:
- 아쉬운 점:

## 액션 아이템
| 할 일 | 종류(예방/감지/대응) | 상태 |
|---|---|---|
| ... | 예방 | 미착수 |
```

## 쓸 때 지킬 것

- **근거 없는 원인 단정 금지.** 로그와 커밋으로 확인된 것과 추측을 구분해서 쓴다.
- **사람을 탓하지 않는다.** "누가 실수했다"가 아니라 "어떤 장치가 없어서 실수가 그대로
  나갔다"로 쓴다.
- **액션 아이템은 실행 가능한 크기로.** "더 조심하기" 같은 건 쓰지 않는다. 테스트 추가, 가드
  스킬 설치(예: `config-drift-guard`, `release-guard`)처럼 구체적인 것만 쓴다.
- 문서를 쓴 뒤 액션 아이템 중 지금 바로 할 것이 있는지 사용자에게 묻는다.
- 파일명의 날짜는 `docs-compliance`의 금지 패턴(`-v1.md` 같은 버전 번호)에 걸리지 않는다.

## 하지 않는 것

- **Vercel/서버 런타임 로그 자동 수집은 하지 않는다.** 사용자가 붙여넣은 것만 쓴다.
- **장애를 직접 고치지 않는다.** 회고 문서를 쓰는 스킬이다 — 수정이 필요하면 별도로 진행한다.
