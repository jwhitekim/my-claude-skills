# codex

Claude Code에서 Codex CLI를 불러 의견을 주고받고, 문서와 프로젝트를 검증하고, 규칙 문서를 작성한다. 특히 Claude의 분석을 Claude 하위 에이전트에게 다시 확인시키는 것만으로 부족할 때, 다른 모델의 독립적인 판단을 얻는 데 쓴다. 하위 에이전트는 Codex 호출과 원문 전달을 맡고, 메인 Claude가 결과를 확인하고 판단한다. 모델이 다르다는 이유만으로 검증 결과가 정확해지는 것은 아니므로 근거를 함께 확인한다.

## 처음 쓸 때

CLI가 없거나 로그인이 필요하면 다음 스크립트로 설치 상태를 확인하고 준비한다. Claude Code에서는 대화형 로그인을 시작하지 않도록 `--no-login`을 쓴다.

```bash
bash ~/.claude/skills/codex/scripts/setup.sh --no-login
```

- 이미 설치되거나 로그인된 단계는 건너뛴다. CLI가 없을 때 npm은 없고 Homebrew가 있으면 Homebrew로 설치한다. 그 외에는 npm으로 `@openai/codex`를 설치하며, npm도 없으면 nvm과 Node.js LTS를 먼저 설치한다(sudo 불필요).
- `--no-login`은 로그인이 필요하다는 안내만 하고 끝날 수 있다. 설치 성공을 로그인 완료로 해석하지 않는다. 인증이 필요하면 사용자에게 Claude Code 프롬프트에서 `! codex login --device-auth`를 실행해 브라우저 승인을 마치도록 안내한다.
- 사용자가 터미널에서 `bash ~/.claude/skills/codex/scripts/setup.sh`를 실행하면 대화형 환경에서는 로그인까지 진행한다. GUI가 있거나 macOS면 일반 로그인, 그 외에는 기기 코드 로그인을 시도한다.
- `ask.sh`와 `review.sh`는 공용 `lib.sh`로 CLI를 찾고, PATH에 없으면 `$NVM_DIR/nvm.sh`(기본 `~/.nvm/nvm.sh`)를 불러 다시 찾는다. 자동 설치나 로그인은 하지 않는다. `lib.sh`를 별도로 실행할 필요는 없다.

## 호출 방법

`ask.sh`와 `review.sh` 호출은 기본적으로 Agent 도구의 하위 에이전트에게 맡긴다. Codex 호출은 몇 분에서 10분 이상 걸릴 수 있고, 실제 검증 호출이 600초 timeout을 넘기기도 했다. Agent의 `run_in_background: true`로 하위 에이전트를 띄워 메인 대화에서 사용자와 계속 소통한다. 긴 중간 실행 출력은 하위 에이전트 쪽에서 다루고, 메인은 최종 답 원문과 실행 정보를 받는다.

메인 Claude가 용도, 검증 범위, Codex에게 보낼 질문과 실행 명령을 정한다. 하위 에이전트의 역할은 **호출과 전달**이다. 사용자는 Claude 하위 에이전트의 검증만으로는 정확성이 부족하다고 보아 Codex를 쓰므로, 하위 에이전트가 답을 스스로 판단·요약·수정하거나 별도 검증으로 대신하지 않는다. Codex의 최종 답 원문과 실행 정보를 돌려받은 뒤 근거 확인, 판단, 사용자 보고는 메인이 한다.

### 하위 에이전트에게 줄 지시

다음 내용을 함께 전달한다. 하위 에이전트가 메인 대화의 맥락이나 명령 옵션을 추측하게 두지 않는다.

- 실행할 정확한 명령: 스크립트 경로, 모든 옵션, 작업 디렉터리와 Codex에게 보낼 프롬프트 전문. `review.sh`의 추가 지시가 없으면 없다고 적는다.
- Bash 호출에 `timeout: 600000`을 지정한다. 오래 걸릴 것으로 예상되면 처음부터 Bash의 `run_in_background: true`를 사용할 수 있다. 실행 중 백그라운드 작업으로 전환되면 반환된 작업 ID로 같은 작업의 완료까지 기다린다. 대기 시간이 지났다는 이유로 같은 명령을 다시 실행하지 않는다. 실제로 종료됐다면 확인된 종료 코드와 오류를 반환한다.
- Codex의 최종 답인 stdout은 생략 없이 원문 그대로 돌려준다. 세션 ID(제공되지 않았으면 그 사실), 성공/실패, 스크립트 종료 코드, stderr 메시지는 답 원문과 구분해 함께 전달한다. 답을 판단·요약·수정하지 않는다.
- 하위 에이전트가 파일을 직접 고치지 않는다. `--write` 작업도 지정된 명령으로 호출한 Codex가 요청 범위 안에서 수정하도록 한다.

예를 들어 메인은 아래처럼 실행 지시와 Codex 프롬프트를 구분해 Agent 도구에 전달한다. `<...>`는 실제 경로와 전문으로 채운다.

```text
역할은 Codex 호출과 결과 전달이다. 아래 명령을 작업 디렉터리
<프로젝트_절대_경로>에서 한 번 실행해 줘.
Bash는 timeout: 600000으로 호출해 줘. 오래 걸릴 것으로 예상되면
처음부터 Bash의 run_in_background: true를 써도 돼.
백그라운드로 전환되면 반환된 작업 ID로 같은 작업의 완료까지 기다려 줘.
대기 시간이 지나도 같은 명령을 중복 실행하지 말고, 실제로 종료되면 그 결과를 돌려줘.
파일을 직접 고치거나 답을 판단·요약·수정하지 마.
stdout 원문은 생략 없이 그대로 돌려줘. 세션 ID(없으면 미제공), 성공/실패,
스크립트 종료 코드와 stderr는 원문과 구분해 함께 돌려줘.

bash ~/.claude/skills/codex/scripts/ask.sh --cd "<프로젝트_절대_경로>" <<'CODEX_PROMPT'
<Codex에게 보낼 프롬프트 전문>
CODEX_PROMPT
```

메인은 `ask.sh`에서 받은 세션 ID를 보관한다. 이어 물을 때는 이 ID를 넣은 정확한 `--resume` 명령과 후속 프롬프트 전문, 작업 디렉터리를 새 하위 에이전트에게 넘기거나, 같은 에이전트에게 SendMessage로 이어 시킨다. 같은 에이전트를 쓰더라도 Codex 세션을 잇는 것은 `--resume <ID>`다.

서로 독립적인 Codex 호출은 하위 에이전트를 나눠 병렬로 실행할 수 있다. 같은 파일을 쓰는 `--write` 호출은 동시에 돌리지 않는다(`--add-dir`가 쓰기를 허용하는 경우도 포함).

아주 짧은 확인은 메인이 직접 실행해도 된다. 예를 들어 이미 설치된 환경에서 `setup.sh --no-login`으로 설치·인증 상태를 점검하는 경우다. 이 스크립트는 CLI가 없으면 설치도 하므로 항상 짧은 것은 아니다. 하위 에이전트를 쓸 수 없는 환경에서는 메인이 Bash의 `run_in_background: true`, `timeout: 600000`으로 Codex를 직접 호출하고 완료 결과를 확인한다.

### 스크립트 사용법

다음은 하위 에이전트에게 전달할 명령 형태다.

```bash
bash ~/.claude/skills/codex/scripts/ask.sh "<프롬프트>"
bash ~/.claude/skills/codex/scripts/ask.sh --write --cd <프로젝트_경로> "<작성 지시>"
bash ~/.claude/skills/codex/scripts/ask.sh --resume <ID> "<후속 질문>"
bash ~/.claude/skills/codex/scripts/review.sh --uncommitted
bash ~/.claude/skills/codex/scripts/review.sh --base main "<추가 지시>"
bash ~/.claude/skills/codex/scripts/review.sh --commit <SHA>
```

옵션은 프롬프트나 추가 지시보다 앞에 둔다. `ask.sh`의 프롬프트와 `review.sh`의 추가 지시는 각각 따옴표로 묶은 인자 하나로 넘긴다. 긴 프롬프트는 `ask.sh`의 stdin으로 전달할 수 있다. 여러 줄이나 셸 문자가 있으면 아래 예시처럼 따옴표 붙인 heredoc을 쓰면 된다.

- 두 스크립트 모두 성공하면 최종 답을 stdout으로 출력한다. `ask.sh`는 성공 시 stderr에 `[codex] session: <ID> ...`를 출력하며, 이 ID로 `--resume`한다. ID를 찾지 못하면 `session: 알 수 없음`을 출력하고, 실패 경로에서는 세션 안내를 출력하지 않는다. `review.sh`는 세션 ID를 제공하지 않으므로 리뷰에 대한 논의는 `ask.sh`에서 새로 시작한다.
- Codex 실행이 실패하거나 최종 답 파일이 비어 있으면 두 스크립트 모두 종료 코드 1로 끝나고, stderr에 Codex 종료 코드가 담긴 실패 메시지와 오류 로그의 마지막 20줄을 출력한다. `ask.sh`는 오류 이벤트도 출력한다. 하위 에이전트는 스크립트 종료 코드와 stderr의 `(exit N)`을 구분해 그대로 전달한다. `(exit 0)`이어도 최종 답이 없어 스크립트가 실패할 수 있다.
- 두 스크립트 모두 `--cd <DIR>`를 지원하며 기본은 호출 시 현재 디렉터리다. `--effort low|medium|high|xhigh`로 추론 강도를 지정할 수 있고, 생략하면 Codex 설정값을 따른다. 복잡한 검증과 리뷰에는 `high`를 고려한다.
- `ask.sh`는 기본 읽기 전용이다. `--write`는 작업 디렉터리와 `/tmp`에 쓰기를 허용한다. 외부 디렉터리도 수정해야 하면 `--add-dir <DIR>`를 쓴다. 이미 존재하는 디렉터리를 지정하며, 반복 지정할 수 있고 `--write`도 포함한다.
- `--resume` 호출도 기본은 읽기 전용이다. 후속 작업에 필요한 `--write`, `--add-dir`, `--cd`, `--effort`는 호출할 때 다시 지정한다. 쓰기 권한은 파일 하나로 제한되지 않으므로 프롬프트에 수정할 파일과 범위를 명시한다.
- Codex가 직접 읽을 수 있는 자료는 경로로 전달한다. 파일에 없는 대화 맥락, 사용자 의도, 제약은 프롬프트에 담는다. 검증과 리뷰는 읽기 전용으로 하고, 파일 수정이 요청된 작업에만 쓰기 옵션을 사용한다.

## 용도별 사용법

### 1. 의견 구하기와 토론

설계 선택, 접근 방식, 막힌 문제를 Codex와 상의한다. 단순히 답을 받아 전달하는 데 그치지 않고, 판단에 필요한 쟁점이 있으면 대화를 이어 간다.

- 첫 질문에 배경, 제약, 선택지와 판단 기준을 담는다. 의견을 구하는 경우에는 Claude의 잠정 판단과 고민도 공유해 검토를 요청할 수 있다. 사용자가 전달할 질문을 지정했다면 원뜻을 유지하고, 필요한 맥락은 구분해 덧붙인다.
- 근거가 약하거나 의견이 갈리면 메인이 구체적인 반론, 추가 자료, 확인할 질문을 정해 하위 에이전트에게 `ask.sh --resume <ID>` 호출을 맡긴다. Codex의 제안을 받아들일 때도 실제 제약에 맞는지 살핀다.
- 판단에 필요한 근거가 충분하거나 남은 쟁점이 분명해지면 마친다. 호출 횟수를 채우거나 합의를 얻기 위해 반복하지 않는다. 새 근거 없이 같은 주장만 반복되면 차이와 불확실성을 정리한다.

사용자에게는 Codex의 핵심 의견과 근거, 중요한 이견, Claude의 최종 판단을 필요한 만큼 정리한다. 짧은 답에도 고정된 보고 형식을 강제하지 않는다.

### 2. 교차검증

Claude의 답, 계획, 분석, 주장을 다른 모델로 확인한다. 독립 풀이와 기존 결론에 대한 비판 중 목적에 맞는 방식을 고른다.

- 독립적인 결론이 필요할 때는 Claude의 결론을 먼저 보여 주기보다 원래 질문, 자료, 조건을 전달한다. 근거는 파일:줄, 실행 결과처럼 확인할 수 있는 형태로 요청하고, 분석을 받은 뒤 결론과 근거를 비교한다.
- 특정 계획이나 답변 자체를 검토할 때는 대상을 그대로 주고 틀린 전제, 빠진 조건, 반례를 확인해 달라고 한다. 문제를 억지로 찾게 하거나 동의를 유도하지 않는다.
- 판단이 갈리면 같은 자료와 조건을 보고 있는지 확인하고, 차이를 만드는 근거를 좁혀 후속 질문한다. 두 모델의 일치만으로 정확성이 입증됐다고 보지 않는다.

### 3. 문서 검증

README, 설계 문서, 스펙, SKILL.md의 설명이 실제 코드와 설정에 맞는지 대조한다. 문서와 관련 구현 경로를 함께 주고, 필요한 경우 상위 지시문과 호출하는 스크립트까지 읽게 한다.

하위 에이전트에게 맡길 명령 예시:

```bash
bash ~/.claude/skills/codex/scripts/ask.sh --effort high <<'PROMPT'
<문서 경로>를 <관련 코드/설정 경로>와 대조해 줘.
명령, 경로, 옵션, 기본값, 실제 동작 설명이 맞는지 확인하고,
불일치와 중요한 누락은 근거(파일:줄)와 함께 알려 줘.
정적 확인과 실제 실행으로 확인한 내용을 구분하고, 확인하지 못한 것은 남겨 줘.
파일은 고치지 마.
PROMPT
```

구현에 있다는 이유만으로 모든 내용을 문서에 추가하지 않는다. 문서의 목적과 독자에게 필요한 누락인지 판단한다.

### 4. 프로젝트 검증과 코드 리뷰

- 변경분 리뷰는 읽기 전용인 `review.sh`를 하위 에이전트에게 호출하게 한다. 범위는 하나만 지정한다. 기본값인 `--uncommitted`는 staged, unstaged, untracked 변경을 포함한다. `--base <브랜치>`는 해당 브랜치와 HEAD의 분기점 대비 현재 작업 트리의 변경을 보며, 커밋하지 않은 추적 파일 변경도 포함한다. 추가 지시가 있을 때 스크립트가 전달하는 범위 설명은 `git diff $(git merge-base HEAD <브랜치>)`다. `--commit <SHA>`는 해당 커밋이 도입한 변경을 본다.
- 추가 지시가 있으면 스크립트가 리뷰 범위를 지시문에 함께 적어 전달한다. 범위 옵션을 CLI에 직접 넘기는 방식과 차이가 있으므로 지적된 파일이 요청 범위에 속하는지 확인한다.
- 프로젝트 전체 점검은 메인이 범위와 우선순위를 정해 하위 에이전트에게 `ask.sh` 호출을 맡긴다. Codex에는 구조, 설정, 테스트, 실행 흐름 등 점검할 대상과 필요한 테스트·빌드의 실행 가능 여부와 결과도 확인하도록 요청한다. 읽기 전용 환경에서 실행이 막히면 수행하지 못한 검증으로 남긴다.
- 문제의 영향, 발생 조건, 근거 위치를 요청한다. 리뷰 결과만으로 프로젝트 전체가 정상이라고 단정하지 않는다. 후속 논의는 리뷰 결과와 관련 경로를 `ask.sh`에 전달해 시작한다.

### 5. 규칙 문서 작성 (CLAUDE.md, AGENTS.md, SKILL.md)

사용자는 Claude가 쓴 규칙 문서가 경직되고 단정적으로 흐르기 쉽고, Codex가 쓴 문서가 의도와 판단 기준을 더 잘 담는다고 평가한다. 이 선호에 따라 새 규칙 문서나 큰 개정은 Codex에 우선 맡긴다. 사용자가 다른 방식을 지시하거나 아주 작은 수정이거나 Codex를 사용할 수 없을 때는 상황에 맞게 직접 처리할 수 있다.

- 사용자 의도, 합의, 대상 문서와 관련 구현 경로, 수정 범위를 정리해 전달한다. 좋은 문체의 예인 `~/.claude/CLAUDE.md`가 있으면 직접 읽고 참고하게 하되, 그 안의 개별 규칙을 다른 문서에 그대로 옮기게 하지는 않는다.
- 의도와 판단 기준이 드러나는 자연스러운 한국어를 요청한다. 실제로 필요한 제약은 분명히 쓰고, 선호나 예시를 예외 없는 의무로 바꾸지 않도록 한다.
- 초안만 필요하면 읽기 전용으로 받는다. Codex가 파일을 직접 수정할 때는 하위 에이전트에게 전달할 명령에 `--write`와 대상 경로를 지정하고, 작업 디렉터리 밖이면 `--add-dir <대상_디렉터리>`도 지정한다. 예를 들어 `~/.claude/CLAUDE.md` 수정에는 `--add-dir ~/.claude`가 필요하다(작업 디렉터리 밖인 경우).
- 결과는 사용자 요구와 실제 동작을 대조해 검토한다. 취향만으로 Claude 문체로 다시 덮어쓰기보다, 의도나 문체를 크게 고칠 필요가 있으면 구체적인 피드백을 주고 Codex와 조정한다. 오탈자나 명백한 사실 오류의 작은 수정까지 재호출할 필요는 없다.

## 결과를 다룰 때

- 하위 에이전트가 돌려준 Codex 원문과 실행 정보를 메인이 확인한다. 원문 전달은 메인에게 하는 반환 방식이며, 사용자에게는 요청에 맞게 메인이 필요한 내용을 정리한다.
- 중요한 지적은 코드, 설정, 실행 결과처럼 확인 가능한 근거로 확인한다. 확인한 사실, 추정, 미검증 항목을 구분하고 Codex의 의견과 Claude의 판단이 갈리면 그 차이를 밝힌다.
- 실패하면 오류에서 원인을 파악한다. CLI 부재는 설치 안내로, 인증 문제는 로그인 안내로 처리한다. 일시 오류나 잘못된 인자처럼 해결 가능한 문제는 원인을 고쳐 제한적으로 재시도하고, 같은 실패를 반복 호출하지 않는다.
- Codex를 쓸 수 없어도 허용된 작업을 진행할 수 있으면 제약을 알리고 가능한 부분을 처리한다. 사용자가 Codex의 검증 자체를 필수로 요구했거나 대체 진행이 결과를 크게 바꾸는 경우에만 필요한 선택을 묻는다. 실패한 검증을 완료로 보고하거나 Claude의 답을 Codex 결과처럼 제시하지 않는다.
