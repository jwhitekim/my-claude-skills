# README 문장·링크·시각 자료 기준

초안과 다듬기에 적용한다. 읽는 사람이 시작에 필요한 정보를 쉽게 찾는지가 기준이다.

## README와 상세 문서

README는 입구다. 분야나 상세 문서 유무에 앞서 무엇인지, 왜 쓰는지, 어떤 결과를 얻는지,
어떻게 처음 시작하는지, 어디서 더 보는지를 보여 주는 공통 범위를 먼저 정한다.

| README에 남길 것 | 상세 문서에 둘 것 |
| --- | --- |
| 무엇을 하고 누구에게 왜 유용한지 짧은 소개 | 긴 배경 설명과 설계 의도 |
| 대표 그림·예시 출력·확인한 결과 한 줄과 최소 범위 표시 | 전체 결과 표, 평가 조건, 한계, 재현 절차 |
| 처음 한 번 실행하거나 이용하는 가장 짧은 시작 경로 하나 | 상세 설치, 다른 실행 방식, 전체 설정·환경변수, 배포·운영·문제 해결 |
| 필요할 때 용도를 설명하는 짧은 구성 개요 | 구성 요소별 아키텍처 설명과 통합 상세 |
| 실제 내용이 있는 상세 문서 링크 | API 참조와 상세 개발 절차 |
| 확인한 라이선스와 필요할 때 짧은 기여·문의·인용 안내 | 상세 기여 절차와 관련 참고 자료 |

- 시작 경로는 처음 써 보는 사람이 한 번 실행해 보는 데 필요한 만큼으로 제한한다.
  명령으로 시작하는 경우 설치부터 첫 실행까지 필요한 명령과 중간 작업을 의존 순서대로 제시한다. 연속 실행할 수 있는 명령은 한 코드 블록으로 묶는다.
  별도 예제 코드가 필요하면 최소 호출 하나를 보여 준다. 서비스 이용이 시작이면 확인한 이용 주소를 둔다.
  필요한 런타임·설정·외부 서비스는 선택한 경로를 기준으로 짧게 밝히고, 실행에 필요한 조건을 생략해 짧아 보이게 만들지 않는다.
- 시작 경로가 여러 준비 단계·설정 설명·실행 방식의 분기로 길어지면 상세 문서로 분리할 신호로 본다.
  처음 한 번 실행하는 데 필요한지, 이후 개발·배포·운영을 위한 설명인지 다시 가른다.
  고정 줄 수를 맞추기보다 독자가 한 경로를 따라 첫 결과를 확인할 수 있는지로 판단한다.
- 오해를 막는 범위는 한 문장으로 남긴다. 예: `이 결과는 파일럿 10문항에서 측정했다.`
  모델의 평가·해석은 출처와 조건을 밝힌다. 확인된 사실이나 일반 성능으로 단정하지 않는다.
- 상세 문서가 없다는 사실은 상세를 README에 넣을 이유가 되지 않는다.
  문서 사이트·`docs/`·`documentation/`·기존 문서 파일에 적절한 목적지가 있는지 확인한다.
  목적지가 없고 상세 안내가 필요하면 `docs/` 문서로 분리하자고 사용자에게 제안한다.
  새 파일은 사용자가 생성을 승인한 범위에서만 만든다.
- 분리가 승인되지 않으면 README에는 공통 범위 안의 소개·대표 결과·시작 경로 등을 남긴다.
  제외한 상세는 작성 결과에서 `상세 문서 후보` 목록으로 보고한다.
  존재하지 않는 파일로 링크하거나 옮기지 않은 내용을 옮겼다고 하지 않는다.
- 코드·설정 불일치나 버그는 README의 경고 상자로 쓰지 않고 작성 결과의 `저장소 문제`로 따로 알린다.
  수정하거나 이슈로 남길지는 사용자가 정한다.
  그 문제로 문서대로 따라 한 시작 경로 자체가 실패한다면 사용자에게 먼저 사실을 알리고 README 처리 방식을 묻는다.
  처리 방식이 정해지기 전에는 해당 경로가 실행되는 것처럼 쓰지 않는다.
- 테스트·CI·레포 규칙이 검사하는 제목·표·행·문구는 보존한다.
  `<details>`로 접을 때도 원래 표와 필요한 제목을 유지하고 관련 검사를 실행한다.
  접기가 검사와 호환되지 않으면 통과하는 형태를 유지한다. 검사를 약화하지 않는다.

## 새 분야 규칙 만들기

[분야별 규칙](templates.md)의 해당 조건에 맞는 분야가 없을 때만 레퍼런스로 새 규칙 초안을 만든다.
같은 분야 대표 README 2~3개를 원문으로 확인한다. 일반 양식 가이드는 실제 사례를 대신하지 않는다.
사용자가 레퍼런스를 직접 지정했다면 기존 규칙이 있어도 지정 원문을 확인한다.
이 경우에도 규칙 추가는 별도 제안이며, 승인 전에는 `templates.md`를 수정하지 않는다.

- 원문 URL과 확인한 버전·커밋 또는 확인 시점을 기록한다. 검색 요약을 원문으로 취급하지 않는다.
- 섹션 구성, 대략적인 줄 수·코드 블록 수, 첫 화면의 소개·그림·배지를 확인한다.
  상세 설치·결과·설정의 문서 목적지와 README에 남긴 내용을 구분한다.
- 문서 목적지가 있는 사례와 없는 사례를 구분한다. 남의 줄 수를 목표로 삼지 않는다.
- 원문을 일부만 받았으면 확인한 범위만 쓴다. 미확보 자료의 구성·분량·생략 항목을 추측하지 않는다.
  확보하지 못한 레포와 이유를 알리고, 확인한 자료와 저장소 근거로 작업을 계속한다.
  근거가 부족한 초안은 미확인 부분을 밝혀 제안한다.

규칙 초안은 다음 틀로 제시한다. README 작업은 진행하되 규칙 파일 추가는 사용자 승인을 기다린다.

```text
분야명:
해당 조건: 저장소에서 확인할 수 있는 분류 기준
대표 결과: 그 분야의 쓰임을 보여 주는 그림·예시 출력·확인한 결과와 선택 기준
첫 화면: 그림·배지·스크린샷의 역할과 선택 조건
시작하기 형태: 공통 README 범위 안에서 처음 한 번 실행하거나 이용할 경로와 선택 기준
근거 레퍼런스: 레포·원문 URL·확인 버전 또는 시점·따른 점·미확인 범위
복사용 뼈대: 확인한 구성으로 만든 Markdown 초안
```

## 명령과 순서

- 명령을 합치거나 옮기기 전에 입력·출력·생성 파일·환경변수·실행 위치를 확인한다.
  뒤 명령이 앞 명령의 결과를 읽으면 그 순서를 유지한다.
- 예를 들어 평가 명령이 앞 단계가 만든 결과 파일을 읽으면, 앞 단계를 평가 뒤로 옮기지 않는다.
  코드 블록을 줄이려고 필수 조건을 빼거나 다른 블록 뒤로 밀지 않는다.
- 요구사항과 최소 예시만 남겨도 실행에 필요한 선행 단계는 코드 또는 연결된 시작 문서에서 찾을 수 있어야 한다.
  검증하지 않은 명령을 실행했다고 보고하지 않는다.

## 문장과 문단

- 한 문장에는 생각 하나만 담는다. 조건이 겹치면 문장을 나누거나 목록으로 푼다.
- 한 문단에는 주제 하나만 담는다. 핵심을 먼저 쓰고, 다른 주제는 문단을 나눈다.
- 표 셀에는 짧은 용도를 쓴다. 상세 설명과 예외는 실제 내용이 있는 상세 문서로 연결한다. 목적지가 없으면 문서 분리 기준에 따라 상세 문서 후보로 보고한다.
- 복사해 실행할 명령은 문장 안에 넣지 않고 코드 블록으로 분리한다.

아래 수치는 영어 개발자 문서 지침이다. 합격 조건이 아니라 **검토 신호**로만 쓰고,
한국어에 고정 단어 수나 문장 수를 만들지 않는다.
수치를 맞추려고 문장을 늘이거나 한 주제를 억지로 쪼개지 않는다.

- 문장 26단어 미만 ([Google 접근성 가이드](https://developers.google.com/style/accessibility#ease-of-reading))
- 문단이 5~6문장을 넘으면 정보가 과한지 검토. 한 주제라면 더 길어도 된다 ([Google 문단 구조 가이드](https://developers.google.com/style/paragraph-structure))

문장을 나누는 기준은 [Google의 짧은 문장 지침](https://developers.google.com/tech-writing/one/short-sentences)을 참고한다.
코드를 표에 넣지 않는 이유는 [Google 표 작성 지침](https://developers.google.com/style/tables#places-not-to-use-tables)에서 확인할 수 있다.

## 링크와 목차

- 저장소 내부 문서는 현재 README 위치를 기준으로 상대 링크를 쓴다.
- 링크 텍스트만 읽어도 목적지를 알 수 있게 쓴다. `여기`, `문서` 같은 이름은 쓰지 않는다.
  예를 들어 `환경변수 설정 안내`, `API 참조`, `배포 절차`처럼 구체적으로 적는다.
- 제목 앵커는 GitHub에서 렌더링된 제목의 링크로 확인한다.
  제목을 바꾸면 목차와 해당 제목을 가리키는 링크도 갱신한다.
- 일반 README의 목차는 섹션 수와 탐색 필요성으로 판단한다. GitHub 자동 Outline도 고려한다.
  짧아도 자주 찾아갈 섹션이 있으면 목차를 둘 수 있다.
- standard-readme 엄격 준수 요청이 있을 때만 명세의 줄 수 기준을 적용한다.
  목차는 100줄 이상이면 필수이고, 100줄 미만이면 선택이다.

근거: [GitHub README의 상대 링크·제목 앵커·자동 목차](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes),
[Google의 의미 있는 링크 텍스트 지침](https://developers.google.com/style/accessibility#links),
[standard-readme 목차 명세](https://github.com/RichardLitt/standard-readme/blob/main/spec.md#table-of-contents-1).

## 시각 자료 선택

시각 자료는 목적에 따라 고른다. 없다는 것 자체를 결함으로 보지 않는다.
이 스킬은 다음 기준을 적용한다.

- UI: 사용 결과를 이해하는 데 도움이 되는 화면 스크린샷을 고른다.
- CLI: 복사할 수 있는 코드와 출력 텍스트를 우선한다.
- 구성 요소 관계·흐름: GitHub에서 지원하는 Mermaid를 쓴다.
- 배지: 빌드 상태나 지원 버전처럼 사용 판단에 필요한 상태만 보여 준다.
- 시연: GIF는 필수가 아니다. 긴 시연은 영상 링크와 텍스트 요약을 함께 둔다.

[GitHub Mermaid 안내](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams)처럼
`mermaid` 코드 블록을 사용한다. 그림 없이도 흐름을 이해할 수 있도록 본문 설명을 붙인다.
Mermaid에는 [`accTitle`과 `accDescr`](https://mermaid.js.org/config/accessibility.html)로 대체 설명도 제공한다.

## 이미지와 대체 설명

- 이미지는 레포 전체에서 찾는다. 숨김 폴더와 git에서 제외된 폴더도 포함한다.
  `node_modules`, `.venv`, `venv`, `.git`, `dist`, `build`, `.next`, 캐시 등 의존성·빌드 폴더는 제외한다.
  `rg --files --hidden --no-ignore`에 해당 폴더의 제외 glob을 적용하고 이미지 확장자로 좁힌다.
- 후보를 직접 열어 확인한다. 같은 그림의 여러 버전이면 논문의 `tex` 참조나 실제 화면의 import 등
  사용 근거로 고른다. 파일명의 `final`이나 수정 시각만으로 결정하지 않는다.
- 각 이미지의 추적 여부를 `git ls-files --error-unmatch -- <경로>`로 확인한다.
  미추적 이미지에는 공개할 파일과 복사할 경로를 제시하고 사용자 확인을 받는다. 확인 전에는 복사·링크하지 않는다.
  다른 README 작업은 계속할 수 있다.
- 확인을 받으면 git 추적 대상인 기존 자산 폴더로 복사한다. 없으면 `docs/images/`를 쓴다.
  목적지가 ignore 규칙에 걸리지 않는지 확인하고 원본은 보존한다. 제외된 원본 경로로 링크하지 않는다.
  복사만으로 git 추적이 시작되지는 않는다. 새 파일의 미추적 상태를 알리고 임의로 스테이징·커밋하지 않는다.
- README에서는 현재 파일 기준의 상대 경로로 연결한다. 이미 추적되는 적절한 이미지면 그대로 쓸 수 있다.
- 이미지에는 alt가 필수다. Markdown은 `![핵심 정보](상대 경로)`, HTML은 `alt` 속성을 쓴다.
  장식용 이미지는 `alt=""`로 둔다. 링크로 쓰는 이미지는 목적지를 설명한다.
- 복잡한 그림에는 짧은 alt와 본문 설명을 함께 둔다. 관계·흐름·결과를 텍스트로도 전달한다.
  긴 설명을 alt에 모두 밀어 넣지 않는다.

근거: [W3C 이미지 대체 텍스트 안내](https://www.w3.org/WAI/tutorials/images/),
[W3C 복잡한 그림의 설명 지침](https://www.w3.org/WAI/tutorials/images/complex/).

다크 모드에서 구분이 어려우면 `<picture>`와 `prefers-color-scheme`으로 이미지를 바꾼다.
아래는 루트 README용 예시다. 실제 파일 경로와 화면 설명으로 바꿔 쓴다.
기본 이미지는 `img`의 `src`에 둔다.

```html
<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/images/result-dark.png">
  <source media="(prefers-color-scheme: light)" srcset="docs/images/result-light.png">
  <img src="docs/images/result-light.png" alt="검색 결과 목록과 선택한 항목의 상세 화면">
</picture>
```

근거: [GitHub의 밝은 모드·다크 모드 이미지 예시](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/quickstart-for-writing-on-github#adding-an-image-to-suit-your-visitors).

## 렌더링 확인

이미지·Mermaid·표를 썼으면 GitHub 미리보기나 렌더링된 파일에서 확인한다.
이미지 경로와 alt, 그림의 밝은 모드·다크 모드 가독성, Mermaid 오류, 표의 줄바꿈을 점검한다.
로컬 미리보기만으로 GitHub 렌더링까지 확인했다고 하지 않는다.
확인하지 못했으면 제시 단계에서 대상과 한계를 밝힌다.
예: `상대 경로는 확인했지만 GitHub에서 이미지·표 렌더링은 확인하지 못했습니다.`

## 사실 확인

- 성능 수치와 비교·우열 표현은 근거·평가 조건·범위를 확인한다.
  모델의 평가는 출처를 밝히고 일반 사실처럼 쓰지 않는다.
- 명령, 경로, 스크립트 이름, 환경변수는 저장소에서 확인한 것만 쓴다. 익숙한 생태계라는
  이유로 `npm start`나 테스트 명령을 추측하지 않는다. 모르면 필요한 정보를 묻거나 `<...>`로 남긴다.
- 기대 출력도 코드·테스트·실행 결과로 확인할 수 있을 때 쓴다. 추측한 성공 메시지를 넣지 않는다.
- 환경변수는 예제 설정을 근거로 이름과 용도를 설명한다. 실제 비밀값 대신 예제 값이나 빈칸을 쓴다.
- 라이선스 종류와 저작권자는 라이선스 파일 등에서 확인한다. 없다고 MIT나 `UNLICENSED`로
  단정하지 말고 확인이 필요한 빈칸으로 남기거나 묻는다.
