# readme-writer

README가 없으면 새로 쓰고, 길면 시작하는 데 필요한 정보가 잘 보이도록 줄인다.
개발자가 무엇을 하는 프로젝트인지 이해하고 설치·사용할 수 있으면 충분하다.
분량을 채우려고 섹션을 늘리지 않고, 시작에 필요한 제약이나 주의점은 남긴다.
초안과 다듬기에는 [문장·링크·시각 자료 기준](style.md)을 적용한다.

## 기본 양식

간단형은 다음 순서를 기본으로 삼는다. 프로젝트에 해당하는 내용만 넣는다.

1. 제목 + 한 줄 설명: 무엇을 하고 왜 유용한지 짧게 쓴다.
2. 시각 자료(선택): 사용 판단이나 결과·구조 이해에 도움이 될 때 고른다.
3. 설치: 요구사항과 설치 명령을 코드 블록으로 적는다.
4. 사용법: 복사해 실행할 수 있는 작은 예시를 담고, 가능하면 기대 출력을 붙인다.
5. 설정·환경변수, 개발(테스트·린트), 기여: 해당할 때만 필요한 내용을 넣는다.
6. 라이선스: 확인한 라이선스와 파일 링크를 마지막 섹션에 둔다.

이 구성은 [standard-readme](https://github.com/RichardLitt/standard-readme/blob/main/spec.md)의
설치·사용·라이선스와 [Make a README](https://www.makeareadme.com/)의 작은 사용 예시를 바탕으로 한다.
[GitHub Docs](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)처럼
개발자의 시작에 필요한 정보에 집중하되, 섹션은 프로젝트에 맞게 고른다.

간단형을
standard-readme 완전 준수로 부르지는 않는다. 명세 준수가 요청되면 필수 기여 섹션 등
[유형별 뼈대](templates.md)의 준수 조건을 적용한다.

일반 README의 목차는 탐색 필요성과 GitHub 자동 Outline을 고려해 고른다.

## 진행 순서

1. **저장소 파악** — 기존 README, 디렉터리 구조, 패키지 설정과 설치·실행 흐름을 읽는다.
   `package.json`의 scripts, `Makefile`, `pyproject.toml`, `.env.example`, `LICENSE`, CI 설정 등이 근거다.
   기존 README가 있으면 본문 언어(한국어/영어)와 제목 언어를 따른다. 없으면 요청 언어와 저장소 관례를 참고한다.
2. **유형 선택** — [유형별 뼈대](templates.md)에서 라이브러리/CLI, 앱/서비스,
   내부 패키지/모노레포 하위 디렉터리, 도구·설정 모음 중 맞는 뼈대를 고른다.
   섞인 프로젝트라면 독자가 처음 해야 할 작업을 중심으로 조합한다.
3. **초안** — 1~2단계에서 모은 사실(명령, 경로, 환경변수, 고른 뼈대)을 정리해 `codex` 스킬로
   Codex에게 초안을 맡긴다. 긴 설명·설계·API 상세는 `docs/` 등으로 링크하게 한다.
   기존 README를 줄이는 작업이면 각 내용을 유지·링크로 대체·삭제 중 어떻게 처리했는지 함께 받는다.
   Codex를 쓸 수 없으면 직접 쓴다.
4. **다듬기** — 초안에 중복 설명이나 독자에게 필요 없는 조건이 있으면 줄인다.
   [문장·링크·시각 자료 기준](style.md)으로 가독성을 점검한다. 필요한 조건과 불확실성은 유지한다.
   한국어 표현이 어색하고 `gemini-rewrite`를 쓸 수 있으면 다듬는다. 쓸 수 없거나 실패하면 직접 다듬는다.
   결과는 원문과 대조해 언어·정보·조건이 유지됐는지 확인한다.
5. **검증** — 다듬은 결과를 `codex` 스킬로 Codex에게 검증받는다(읽기 전용). 다음을 확인한다.
   - 명령, 경로, 스크립트 이름, 환경변수, 상대 링크가 저장소와 맞는지
   - Codex 초안과 비교해 다듬으면서 빠진 조건·주의점이 있는지, 문장이 다시 단정적으로 바뀐 곳이 있는지
   - 기존 README를 줄였다면 원본의 필수 설정·제약·지원 경로가 최종본에 남았거나 유효한 문서로 연결됐는지
   - 제목 앵커가 맞는지, 이미지·Mermaid·표가 GitHub에서 제대로 렌더링되는지

   지적은 Claude가 저장소에서 직접 확인한 뒤 반영한다. 재검증 반복 여부는 `codex` 스킬의 재검증 종료 기준을 따른다. 링크 존재처럼 바로 확인할 수 있는 것은
   Claude가 먼저 점검해도 된다. Codex를 쓸 수 없으면 Claude가 대조하고 그 사실을 알린다.
6. **제시** — 완성한 README 또는 파일 변경을 짧은 요약과 함께 보여 준다.
   GitHub 렌더링 등 확인하지 못한 항목을 밝힌다. 기존 README를 줄였다면 어느 문서로 연결했는지,
   무엇을 삭제했는지 사용자에게 알린다.

## 작성할 때의 판단

- 우선순위는 사용자의 명시 요구, 저장소의 문서 규칙과 기존 README 관례, 유형별 뼈대와 기본 기준 순이다.
  어떤 저장소 근거로 섹션·형식을 골랐는지 설명할 수 있게 한다.
- 성능 수치와 비교·우열 표현은 확인 가능한 근거가 있을 때만 쓴다.
- 명령, 경로, 스크립트 이름, 환경변수는 저장소에서 확인한 것만 쓴다. 익숙한 생태계라는
  이유로 `npm start`나 테스트 명령을 추측하지 않는다. 모르면 필요한 정보를 묻거나 `<...>`로 남긴다.
- 기대 출력도 코드·테스트·실행 결과로 확인할 수 있을 때 쓴다. 추측한 성공 메시지를 넣지 않는다.
- 환경변수는 예제 설정을 근거로 이름과 용도를 설명한다. 실제 비밀값 대신 예제 값이나 빈칸을 쓴다.
- 라이선스 종류와 저작권자는 라이선스 파일 등에서 확인한다. 없다고 MIT나 `UNLICENSED`로
  단정하지 말고 확인이 필요한 빈칸으로 남기거나 묻는다.
- 짧게 만드는 목적은 중복과 장황한 설명을 줄이는 것이다. 필수 설정·제약·지원 경로는
  길다는 이유만으로 없애지 않는다. 별도 문서가 있으면 링크해 독자가 찾을 수 있게 한다.
