# readme-writer

README는 입구다. 작성 전에 [README와 상세 문서의 공통 범위](style.md#readme와-상세-문서)를 확인한다.
분야나 상세 문서 유무에 따라 범위가 넓어지지 않도록 이 기준을 먼저 적용한다.
초안과 다듬기에는 [문장·링크·시각 자료 기준](style.md)을 적용한다.

## 기본 양식

공통 범위 안에서 [분야별 규칙과 뼈대](templates.md)를 저장소 근거로 고른다.
분야 규칙은 대표 결과와 처음 해 볼 일 하나를 정하는 데 쓴다.
설치·설정·개발 섹션을 일괄 추가하지 않는다.
standard-readme 엄격 준수가 요청되면 [별도 준수 조건](templates.md#standard-readme-엄격-준수)을 적용한다.

## 진행 순서

1. **저장소 파악** — 기존 README, 디렉터리 구조, 패키지 설정과 설치·실행 흐름을 읽는다.
   `package.json`의 scripts, `Makefile`, `pyproject.toml`, `.env.example`, `LICENSE`, CI 설정 등이 근거다.
   문서 사이트·`docs/`·기존 문서 파일에 어떤 상세가 있는지 확인한다.
   테스트·CI·레포 규칙이 README의 제목·표·행·문구를 검사하는지도 찾는다(`tests/layout` 등).
   기존 README가 있으면 본문 언어(한국어/영어)와 제목 언어를 따른다. 없으면 요청 언어와 저장소 관례를 참고한다.
2. **분야 규칙 선택** — 저장소 파악 결과를 [분야별 해당 조건](templates.md)과 대조해 규칙을 고른다.
   여러 분야에 걸치면 독자가 처음 할 일을 중심으로 조합한다. 기존 규칙이 맞으면 레퍼런스를 검색하지 않는다.
   맞는 규칙이 없을 때만 같은 분야 대표 README 2~3개를 원문으로 확인해 [규칙 초안](style.md#새-분야-규칙-만들기)을 만든다.
   사용자에게 `templates.md`에 추가할지 제안하되 승인 전에는 추가하지 않는다.
   사용자가 레퍼런스를 직접 지정한 경우에도 해당 원문을 확인한다.
3. **초안** — 처음 해 볼 일 하나와 그 시작 경로를 정한다. 코드·설정 불일치나 버그는 README에 넣지 않고 [저장소 문제](style.md#readme와-상세-문서)로 모은다.
   저장소 근거·선택한 분야 규칙·시작 경로·문서 분리 계획을 정리해 `codex` 스킬로 Codex에게 초안을 맡기고, 공통 README 범위도 함께 전달한다.
   검사 대상 내용은 삭제하지 않고 `<details>`로 접는 등 검사와 호환되는 형태로 바꾼다.
   이미지 탐색·추적 상태·공개 확인과 명령 의존성은 [상세 기준](style.md)을 따른다.
   기존 README를 줄이는 작업이면 각 내용을 유지·링크로 대체·삭제 중 어떻게 처리했는지 함께 받는다.
   Codex를 쓸 수 없으면 직접 쓴다.
4. **다듬기** — 중복 설명을 줄이고, 처음 한 번 실행하는 범위를 넘어선 상세가 남았는지 살핀다.
   상세의 이동·새 문서 제안·승인되지 않은 내용의 처리는 [문서 분리 기준](style.md#readme와-상세-문서)을 따른다.
   한국어 표현이 어색하고 `gemini-rewrite`를 쓸 수 있으면 다듬는다. 쓸 수 없거나 실패하면 직접 다듬는다.
   결과는 원문과 대조해 언어·조건·불확실성이 유지됐는지 확인한다.
5. **검증** — 다듬은 결과를 `codex` 스킬로 Codex에게 검증받는다(읽기 전용).
   검증 요청에 공통 README 범위와 선택한 시작 경로를 전달한다.
   범위 밖 지적은 README 수정 제안과 구분해 표시하도록 요청한다. 다음을 확인한다.

   - 명령, 경로, 스크립트 이름, 환경변수, 상대 링크가 저장소와 맞는지
   - 명령을 합치거나 순서를 바꿨다면 앞 명령의 출력·생성 파일에 대한 의존성이 유지됐는지
   - 선택한 시작 경로에 처음 한 번 실행하는 데 필요한 조건과 명령이 갖춰져 있는지
   - 상세 설치·배포·운영·문제 해결이나 저장소 문제 설명이 README에 섞이지 않았는지
   - 모델의 평가나 제한된 측정 결과가 일반 사실로 바뀌지 않았는지
   - README를 검사하는 관련 테스트·CI 검사를 통과하는지
   - 제목 앵커가 맞는지, 이미지·Mermaid·표가 GitHub에서 제대로 렌더링되는지

   지적은 Claude가 저장소에서 확인하고 README 범위인지 판단한 뒤 반영한다.
   “빠지면 실행이 실패한다”는 지적도 선택한 시작 경로에 필요한 조건인지 먼저 확인한다.
   범위 밖의 사용 안내는 내용이 있는 기존 상세 문서로 연결하고, 적절한 목적지가 없고 새 문서 생성이 승인되지 않았으면 `상세 문서 후보`로, 코드·설정 불일치나 버그는 `저장소 문제`로 돌린다.
   시작 경로 자체가 실패하면 [문서 분리 기준](style.md#readme와-상세-문서)에 따라 사실을 알리고 README 처리 방식을 사용자에게 묻는다.
   재검증은 `codex` 스킬의 종료 기준을 따른다.
   링크 존재처럼 바로 확인할 수 있는 것은 먼저 점검해도 된다.
   Codex를 쓸 수 없으면 Claude가 대조하고 그 사실을 알린다.
6. **제시** — 변경 요약과 적용한 분야 규칙을 알린다. 조합했다면 그 이유도 짧게 설명한다.
   새 분야 규칙을 제안하거나 지정 레퍼런스를 확인했다면 근거 레포·원문 링크·따른 점을 알린다.
   원문 미확보나 GitHub 렌더링 등 확인하지 못한 항목을 밝힌다.
   어느 문서로 상세를 넘겼는지, 무엇을 삭제했는지도 알린다.
   분리가 승인되지 않아 README에서 제외한 상세는 `상세 문서 후보` 목록으로 보고한다.
   코드·설정 불일치나 버그는 `저장소 문제`로 따로 알리고, 수정하거나 이슈로 남길지는 사용자가 정하도록 한다.
   규칙·레퍼런스·저장소 문제 보고를 README 본문에 넣지는 않는다.

## 판단 기준

사용자의 명시 요구 → 저장소의 명시 문서 규칙과 검사 대상 보존 조건 → 공통 README 범위 → 기존 README의 언어·표현 관례와 분야별 규칙 순으로 적용한다.
명령·출력·성능·환경변수·라이선스는 [사실 확인 기준](style.md#사실-확인)에 따라 저장소 근거로 쓴다.
